# Figma → код

Пошаговый процесс сборки компонента из макета.

## Порядок: статика → анимация

Если у макета помимо обычного статичного состояния есть покадровая анимация
(`anim`-токены и/или сцены из нескольких фреймов, см. «Покадровые сцены» ниже) —
делать это двумя проходами, не одним:

1. **Фаза 1 — статика.** Пройти шаги 1-6 целиком по статичным фреймам, без
   анимации: структура, разбивка на компоненты, токены, flow-layout вместо
   `absolute`, визуальная сверка на всех брейкпоинтах. Если пользователь сразу
   даёт и статику, и анимационные кадры — всё равно сначала закончить и
   сверить статику, потом переходить к анимации, а не мешать оба слоя в одном
   проходе: так проще держать в голове одно измерение задачи за раз (сначала
   «как выглядит в покое», потом «как двигается»), и анимация ложится поверх
   уже правильного flow-layout, а не подстраивает структуру под координаты
   конкретного кадра.
2. **Фаза 2 — анимация поверх готовой статики.** Разобрать `anim`-токены и/или
   покадровые сцены и добавить их отдельным слоем (`transform`/`opacity` в
   компонентах, хуки из `anim.tsx`/`motion`, GSAP + ScrollTrigger) — не
   переписывая уже готовую структуру, за исключением точечных правок под
   FLIP-переходы между секциями (см. «Покадровые сцены»).

Если пользователь просит сверстать макет и упоминает, что анимация будет
отдельно/потом — не ждать её, чтобы начать: собрать статику сразу, а про
анимационные кадры спросить отдельным заходом, когда они будут готовы.

## 1. Проверить связь с Figma

Убедиться, что MCP-сервер `figma` отвечает (в Figma Desktop открыт нужный файл,
выделен фрейм). Если пользователь работает удалённо — туннель должен быть поднят
(см. CLAUDE.md, раздел «Figma MCP»). Если инструменты Figma MCP недоступны —
сказать об этом прямо и попросить открыть файл/поднять туннель, не гадать по памяти.

## 2. Собрать все версии макета для страницы

В начале работы над каждой страницей спросить у пользователя ссылки на все три
версии макета — мобильную, планшетную и десктопную (например, в этом проекте
фреймы называются `Mobile_375`, `Tablet_768`, `SNAPA`/desktop). Не начинать
вёрстку по одной версии в расчёте достроить остальные "потом": разные брейкпоинты
в этом Figma-файле — это не автогенерация одного макета, а отдельно
спроектированные раскладки (другой порядок элементов, другое поведение
компонентов вроде цветового слайдера или списка характеристик), и без них
переходы между брейкпоинтами придётся додумывать самому.

Эти три версии дают конкретные опорные точки (min/mid/max) для `clamp()` из
раздела «Флюидная вёрстка» — не гадать промежуточные значения, а брать реальные
ширину/размер шрифта из мобильного и десктопного фрейма как границы диапазона,
и сверяться с планшетным как контрольной точкой посередине.

Если пользователь даёт только одну версию — явно уточнить, есть ли остальные,
прежде чем проектировать адаптив.

## 3. Забрать данные макета

Для текущего выделения (по каждой из трёх версий) вызвать по необходимости:

- `get_metadata` — структура/иерархия фрейма, чтобы понять на что бить компонент;
- `get_code` — сгенерированная Figma разметка/стили как отправная точка;
- `get_variable_defs` — переменные (цвета, отступы, типографика), которые должны стать
  токенами в `@theme` (`src/index.css`), а не хардкодом;
- `get_image` — растровый снимок фрейма для визуальной сверки и экспорт картинок/иконок
  в `src/assets/`.

Из `get_metadata` вытащить `anim`-токены — дизайнер пишет их в скобках в конце
имени слоя (`Hero-title (anim: fade-up; delay: 100)`). Разобрать их и учесть при
разбивке на компоненты (см. раздел «Анимации» ниже). Если у слоёв токенов нет, а
макет явно предполагает движение — спросить у пользователя, а не додумывать.

Если фреймы образуют покадровую сцену (несколько фреймов подряд показывают один
экран в разные моменты скролла/анимации) — собрать `get_metadata` по всем кадрам
сцены, не только по одному, и сопоставить элементы по имени слоя (см. «Покадровые
сцены» ниже).

## 4. Спроектировать разбивку на компоненты

Не переносить макет в один плоский файл. Разбить по смысловым блокам (шапка, карточка,
секция и т.п.), как это обычно делается в React: один компонент — один файл в
`src/components/`. Переиспользуемые элементы (кнопка, инпут) — выделять отдельно, если
повторяются в макете 2+ раза.

## 5. Свести токены

Новые цвета/шрифты/отступы из `get_variable_defs` добавить в `@theme` в
`src/index.css`, если их там ещё нет, и использовать через Tailwind-классы
(`bg-brand`, `text-heading` и т.п.), а не через произвольные значения в JSX.

## 6. Собрать и сверить

Написать компонент(ы), запустить `npm run dev`, визуально сверить с `get_image` /
макетом на всех трёх ширинах (мобильной/планшетной/десктопной), включая
промежуточные значения между ними — не только сами брейкпоинты.
Прогнать `npm run lint` и `npm run format` перед тем как считать задачу готовой.

## Анимации (anim-токены)

Фаза 2 из раздела «Порядок: статика → анимация» — выполнять после того, как
статичная вёрстка собрана и сверена, а не параллельно с ней.

Дизайнер задаёт анимацию элемента прямо в имени слоя Figma — токеном в скобках
после имени/класса. Полный справочник по синтаксису и ключам — `ANIMATION-TOKENS.md`
в корне проекта (та же шпаргалка отдаётся дизайнеру). Кратко:

```
ИмяСлоя (anim: <эффект>; trigger: <триггер>; dur: <мс>; delay: <мс>;
         ease: <кривая>; distance: <px>; stagger: <мс>; once: <bool>;
         start/end: <точки скролла>)
```

`anim` обязателен, остальное — с дефолтами (`trigger: in-view`, `dur: 600`,
`delay: 0`, `ease: out`, `distance: 24`, `once: true`).

### Как переносить в код

1. **Разобрать токены из `get_metadata`.** Токен на контейнере со `stagger`
   относится к его прямым детям — они анимируются по очереди; собственный токен
   ребёнка переопределяет родительский для этого ребёнка.
2. **Простые случаи — через `src/lib/anim.tsx`, без зависимостей:**
   - `fade`/`fade-up`/`fade-down`/`fade-left`/`fade-right`/`scale`/`blur-in` на
     `trigger: in-view` или `load` → `<Reveal effect delay duration distance trigger>`.
   - `stagger` на контейнере → обернуть детей в `<Stagger step={<stagger>}>`
     (дети — `<Reveal>` или любой компонент с пропом `delay`).
   - `anim: count` → `useCounter(target, { duration })`, `ref` на элемент с числом,
     конечное значение — из текста слоя.
3. **Скролл-эффекты — ставить библиотеку по факту, не заранее:**
   - `trigger: scroll`, `anim: parallax` → `npm i motion`, использовать
     `useScroll` + `useTransform`.
   - `anim: pin` и сложные скролл-сцены → `motion` или GSAP + ScrollTrigger;
     таймлайн из токена не восстановить — спросить у пользователя описание
     последовательности или ссылку на прототип.
4. **`ease: spring`** → `motion` (`type: 'spring'`) либо пружинный
   `cubic-bezier`; для остального хватает `cubic-bezier(0.16, 1, 0.3, 1)`
   (уже зашит в `anim.tsx` как `ease: out`).
5. **`prefers-reduced-motion`** гасится глобально в `src/index.css` — отдельно
   ничего делать не нужно, но проверить, что при включённой настройке контент
   виден сразу (не остаётся `opacity: 0`).
6. **Не оборачивать в `<Reveal>` элементы без токена.** Нет токена и макет не
   намекает на движение — статичный элемент.

Держать анимации дешёвыми: анимировать только `opacity`/`transform`/`filter`,
`will-change` — точечно, не на десятках элементов сразу (перекликается с
разделом «Производительность»).

## Покадровые сцены (одинаковое имя слоя между фреймами)

Кроме одиночных `anim`-токенов (эффект на одном фрейме) в макете могут быть
последовательности фреймов, покадрово показывающие один и тот же экран в разные
моменты скролла/анимации — сцена целиком. Если в двух и более таких фреймах
элемент называется одинаково, это один и тот же элемент в разных состояниях
(позиция/размер/поворот/прозрачность), а разница между кадрами — его
анимационный путь.

### Как опознать и собрать сцену

1. Сцена — фреймы с общим базовым именем и явным порядковым номером
   (`Scene-Hero_01`, `Scene-Hero_02`, ...). Если порядок кадров не очевиден из
   названия — спросить у пользователя, не угадывать (как с версиями макета в
   шаге 2).
2. По каждому фрейму сцены вызвать `get_metadata` и сопоставить элементы по
   точному имени слоя (регистр и пробелы важны — Figma сама плодит суффиксы у
   копий вроде `Title copy`/`Title 1`, такие расхождения не считать разными
   элементами автоматически, а сверить с пользователем). Элемент, которого нет
   в соседнем кадре — значит появляется/исчезает (mount/unmount), а не
   сдвигается.
3. Для каждого сопоставленного элемента сравнить координаты/размер (и
   rotation/opacity, если отданы) между соседними кадрами — это опорные точки
   (keyframes) движения, а не всё движение целиком: кривую (easing) между ними
   выбрать по смыслу анимации или спросить, если неочевидно.

### Как переносить в код

- Сцена держится на месте, пока элементы внутри неё двигаются (пин) → паттерн
  «Пиновая пошаговая секция» ниже: секция `height: N×100vh`, sticky-обёртка,
  GSAP-таймлайн, где шаги — это и есть кадры сцены, `ScrollTrigger` скрабит
  таймлайн по прогрессу скролла.
- Элемент физически переходит из одной секции лендинга в другую (не внутри
  одного пина, а между независимыми блоками) → кандидат на FLIP-переход:
  элемент выносится в общий overlay-слой поверх обеих секций
  (`position: fixed`/`sticky` на всю зону перехода) и анимируется от координат
  в секции A к координатам в секции B по прогрессу скролла границы между ними.
- Координаты из `get_metadata` — абсолютные px под ширину конкретного фрейма
  (обычно десктопного). Не переносить их как жёсткие px в код — прогнать через
  ту же логику из «Флюидная вёрстка» (проценты/`clamp()` от контейнера), иначе
  сцена сломается на других ширинах.
- Сцена почти всегда специфична под десктоп: на мобильном/планшетном такие
  многошаговые сценарии часто сильно упрощают или убирают вовсе. Явно спросить
  у пользователя, нужна ли сцена на всех трёх версиях макета или это
  desktop-only поведение, а на мобильном/планшете — обычный `anim`-токен или
  статика.
- Если между кадрами меняется не только позиция, а что-то, что трудно
  объяснить одной плавной анимацией (например форма, цвет и текст
  одновременно) — не считать это автоматически одним переходом, спросить у
  пользователя, что имелось в виду.

## Скролл-нарратив (пины, «наезд», скролл-прогресс)

Для `anim: pin` / `trigger: scroll` и лендингов со скролл-сценами. Паттерны
проверены на реальных проектах — не изобретать заново.

**Либы (ставить по факту).** Простой parallax/scrub одного элемента → `motion`
(`useScroll` + `useTransform`). Настоящий пиновый многошаговый нарратив →
Lenis + GSAP + ScrollTrigger (`npm i lenis gsap`).

**Мост Lenis ↔ ScrollTrigger** — обязателен, иначе позиции рассинхронятся:
`lenis.on('scroll', ScrollTrigger.update)`; гнать `lenis.raf` из
`gsap.ticker`; `ScrollTrigger.refresh()` после готовности **и** ещё раз после
загрузки ленивых картинок ниже fold (`img.onload`) — высота страницы меняется
после первого расчёта, триггеры уезжают. На инстансе Lenis **не задавать
`duration`** (ломает `lerp` для колеса); вес скролла — `wheelMultiplier`
(меньше = тяжелее), плавность — `lerp` (~0.1 старт).

**Пиновая пошаговая секция:** высокая внешняя секция (`height: N×100vh`) +
`sticky` pin-ребёнок (`position: sticky; top: 0; height: 100vh`, перекрывает все
строки) + невидимые marker-элементы (`opacity:0; pointer-events:none`, по одному
на 100vh) как цели `IntersectionObserver` (threshold 0.5) — только сенсоры шага,
сами не анимируются. Активный шаг → класс-состояние → CSS/GSAP.

**«Наезд» (ride-over):** следующей секции — `margin-top: -100vh` +
`position: relative` + `z-index` на единицу больше перекрываемой. z-index ставить
на **секцию**, не на внутренний пин (конкурирует только внутри своего stacking
context). Перекрываемой пиновой секции — лишняя завершающая `100vh` строка-буфер,
чтобы наезд ел мёртвое место, а не время просмотра последнего шага.

**Непрерывный скролл-прогресс** (shrink/parallax/scrub, не пошагово): невидимый
marker + `getBoundingClientRect()` на `scroll` / `lenis.on('scroll')`, clamped
0–1, писать инлайн `style` каждый тик. **Без CSS `transition`** на этих свойствах
— фигтит с непрерывным обновлением, даёт джиттер.

**Устойчивость ScrollTrigger:**

- Не `start: 'top top'` на секции у низа страницы или с `margin-top: -Nvh` — точка
  недостижима, триггер молча не сработает; брать процент (`'top 10%'`).
- `start`/`end` как функция `() => …`, а не снятое один раз число, если геометрия
  зависит от ленивого контента (GSAP переусчитает на `refresh()`).
- `gsap.killTweensOf(target)` в начале каждого enter/exit — быстрый скролл вызовет
  колбэк чаще, чем твин успевает завершиться, шаги наложатся.
- «B стартует там, где кончил A» → дать B **свой** ScrollTrigger с `start` = `end`
  триггера A. **Никогда не аппендить твин B в scrub-таймлайн A** — меняет общую
  длительность таймлайна и пересчитывает scroll-прогресс всех твинов A.

**Разбитый по буквам/строкам текст (SplitText и аналоги):** `line-height` ~1.18
на разбиваемых заголовках — маска (`overflow: clip`) иначе режет хвосты букв
(g/p/y, кириллица у/р/д/ц) и в покое тоже. Любой замер текста — после
`document.fonts.ready`. Ре-сплит на resize.

**`scroll-snap-type` + `position: sticky` на одной странице фризит скролл** в
части браузеров — не совмещать; «долистывание до секции» делать программным
`scrollTo`.

**Якорные ссылки:** мерить оффсеты целей один раз при `scrollY === 0` и
кешировать, ре-мерить только на resize. Живой замер, когда между позицией и целью
есть `sticky`/scrub-секция, вернёт неверное число.

**`yPercent: 100`** (не `y: '100vh'`, не `yPercent: 50`) для «выезжает снизу
из-за собственного края».

## Флюидная вёрстка

Верстать флюидно — размеры (шрифты, отступы, ширины блоков) должны непрерывно
масштабироваться под ширину вьюпорта, а не только переключаться между
несколькими фиксированными брейкпоинтами.

**Приём по умолчанию — rem-скейлинг корня, не `clamp()` в компонентах**
(как в Nordhaus/Snapa). В `src/index.css` `font-size` у `html` задаётся через
`vw`, отдельно для каждой брейкпоинт-зоны, откалиброванный так, чтобы
`1rem = 16px` ровно на ширине эталонного Figma-фрейма этой зоны:

```css
html {
  font-size: 0.83333vw; /* 16px при 1920px — Desktop */
}
@media screen and (max-width: 61.9375rem) {
  /* ≤991px — Tablet */
  html {
    font-size: 2.08333vw; /* 16px при 768px */
  }
}
@media screen and (max-width: 30rem) {
  /* ≤480px — Mobile */
  html {
    font-size: 4.10256vw; /* 16px при 390px (взять реальную ширину
      мобильного Figma-фрейма — не всегда 390) */
  }
}
```

Формула коэффициента: `(16 / W) * 100`, где `W` — ширина эталонного
Figma-фрейма этой зоны в px. Длины в `@media` — в `rem`, не в `px`: спецификация
резолвит их по дефолтному (16px) размеру шрифта браузера, а не по
переопределённому этим же правилом, так что зацикливания нет — `61.9375rem`
и `30rem` эквивалентны `991px`/`480px`.

После этого в компонентах используются **литеральные `rem`-значения из
макета** на каждом Tailwind-брейкпоинте (без префикса — Mobile, `md:` —
Tablet, `lg:` — Desktop; см. «Только относительные единицы» ниже) — никакого
`clamp()`/`calc(...vw)` в самих className. Плавность между и за пределами
брейкпоинтов даёт корневой rem-скейлинг сам по себе: браузер пропорционально
масштабирует любой `rem` вместе с шириной вьюпорта внутри зоны, а скачок
остаётся только ровно на границе брейкпоинта — там, где и в самом макете
меняется дизайн. Если у макета нет отдельной версии для диапазона между двумя
существующими брейкпоинтами (например, между Tablet 768 и Desktop 992+) —
не выдумывать промежуточные значения: rem-скейлинг уже сглаживает эту зону
достаточно (проверено — без него literal-брейкпоинт-переключение на
desktop-значение прямо на границе даёт наложение элементов на промежуточных
ширинах вроде 1280/1366px, с ним то же значение на той же ширине оказывается
пропорционально меньше и не ломает раскладку).

- Голый `px` в Tailwind-классах не использовать вообще, даже для величин,
  одинаковых на всех брейкпоинтах макета (иконка 100px и на mobile, и на
  desktop — не значит `size-[100px]`, значит `size-25`/`size-[6.25rem]`). Всё —
  `rem`/`%`/`vw`/`vh`/`em`/`fr`. Исключение — `border`-толщина через
  Tailwind-утилиту `border`/`border-b` без арбитрарного значения (браузерный
  дефолт 1px, hairline, его не масштабируют нигде в вебе); если для проекта
  и это неприемлемо — сказать явно, не решать самостоятельно.
- Круглые Tailwind-значения (кратные `0.25rem`) — через числовые утилиты
  (`w-85`, `size-25`, `py-15`, `gap-10`), не через `[]`-арбитрары: они уже
  в rem под капотом и читаются лучше. Для значений не на этой сетке (нечётные
  `rem`, кастомная типографика) — `text-[3.4375rem]` и т.п.

`clamp()` остаётся резервным приёмом — годится точечно там, где корневой
rem-скейлинг по какой-то причине недоступен/нежелателен (например, встраивание
компонента в чужую страницу с фиксированным root font-size). Формула для этого
случая (b — px-константа, переводится в rem перед записью, чтобы не смешивать
с голым px):

```
m = (v2 - v1) / (w2 - w1)      // px на px ширины вьюпорта
b = v1 - m * w1                 // px, затем /16 → rem
clamp(v1rem, calc(b_rem + (m*100)vw), v2rem)
```

## Человекочитаемые имена

Figma отдаёт код с техническими именами слоёв (`Frame 2131328216`,
`Rectangle 2085654480`) и `data-node-id` — их нельзя переносить в итоговый код
как есть. Имена компонентов, файлов, переменных и кастомных CSS-классов
(в `@theme`, если нужны классы вне Tailwind-утилит) должны отражать смысл
блока, а не структуру Figma-документа: любой разработчик должен понять
назначение по имени, не открывая макет.

- `Frame 2131328216` → `HeroSection`, `CharacteristicsList`, `PresetCard` и т.п.
  по смыслу блока, а не по номеру слоя.
- `data-node-id` и прочие Figma-специфичные атрибуты из финального кода убирать.
- Токены в `@theme` называть по роли (`--color-brand`, `--font-size-heading`),
  а не по имени Figma-стиля (`Title/H2/Desktop` → `heading-lg` и т.п.).

Это правило про технические авто-имена. Осмысленные имена, которые дизайнер
сам задал слоям (`Hero-text-left`, `Intro-bottom-wrap`, `Qualities-item-title`
и т.п.) — наоборот, переносить в код как есть: каждому такому элементу
(секция, текстовый блок, картинка, обёртка) — className, совпадающий с именем
слоя, первым токеном в списке классов, рядом с Tailwind-утилитами
(`className="Hero-text-left whitespace-nowrap text-[...]"`). Так структура
кода 1:1 матчится с макетом, и правки в Figma проще сопоставлять с кодом.

## Layout вместо абсолютных координат

Figma-экспорт почти всегда кладёт слои через `absolute` + `left-[Npx]/top-[Npx]`
— так устроен сам формат Figma, но для веба это ломает флюидность сильнее, чем
фиксированные px в шрифтах: абсолютные координаты вообще не адаптируются под
другую ширину. Переводить такую разметку в обычный поток:

- flexbox/grid с `gap` вместо `left`/`top`-координат везде, где слои на самом
  деле идут друг за другом (секции, списки, колонки);
- `absolute`/`inset` оставлять только для реально наложенных друг на друга
  элементов (бейджи поверх картинки, декоративные блики, оверлеи-градиенты) —
  то, что в макете и задумано как слой поверх другого;
- у обёртки такого наложения должен быть `relative`-контейнер с размером,
  заданным через flow (не через фиксированные px), чтобы оверлей масштабировался
  вместе с содержимым.

## CSS-ловушки при переносе

Реальные грабли с лендингов — проверять при переносе:

- **`<img>` → `display: block`.** Дефолтный `inline` оставляет несколько px
  baseline-зазора снизу, переполняющего обёртку `height: 100%`. Обёртке с
  `object-fit: cover` — свой `overflow: hidden`.
- **`inset: 0` не растягивает элемент, если заданы явные `width`/`height`**
  (`100vw`/`100vh` вместо `100%`) — явный размер побеждает, right/bottom молча
  игнорируются.
- **`left: 50%` + `translateX(-50%)` хрупко на элементе, чью ширину анимирует JS**
  — предпочесть `justify-self: center` на самом grid-элементе.
- **`flex: 1`-ребёнок в `flex-direction: column` игнорирует `overflow-y: auto`
  без `min-height: 0`** — flex-элементы по умолчанию `min-height: auto`.
- **z-index конкурирует только внутри своего stacking context** — если секция
  сама создаёт контекст (`position` + `z-index`), z-index её ребёнка ограничен
  z-index'ом секции.
- **Не давать элементу, которым управляет JS-анимация (GSAP/motion), сырой CSS
  `transform` как resting-состояние** — ломает трекинг `yPercent`/`scaleY` на
  инициализации. Прятать через `visibility: hidden` / `opacity: 0`, трансформ
  отдать библиотеке.
- **Keyword-радиусы (`circle(farthest-corner at …)`) не анимируются `transition`**
  надёжно — для `clip-path`-reveal с переходом брать плоский увеличенный процент
  (`150%`).
- **`will-change` спекулятивно («вдруг уберёт мерцание») делает хуже** — ставить
  только по подтверждённому репро конкретной точки.
- **Концентрический радиус** (кольцо/бордер + вписанный фон): внутренний =
  `calc(внешний − толщина_бордера)`, не копировать литеральное значение из Figma.

## Адаптивные изображения

Figma отдаёт одну картинку под конкретный размер фрейма (обычно десктопную) —
для продакшена этого недостаточно.

- Использовать `srcset`/`<picture>` или хотя бы несколько размеров экспорта,
  чтобы не грузить десктопную картинку на мобильном;
- `object-fit` (`cover`/`contain`) + заданный через CSS `aspect-ratio` вместо
  фиксированных `width`/`height` из Figma, чтобы картинка не искажалась и не
  ломала раскладку на других пропорциях экрана;
- `alt`-текст — по смыслу изображения, не по имени файла/слоя из Figma.

## Container queries для переиспользуемых компонентов

Если один и тот же компонент (карточка, кнопка, превью) в макете встречается
в разных по ширине контейнерах — адаптировать его через container queries
(`@container` в Tailwind v4), а не только через медиа-запросы на вьюпорт.
Компонент должен подстраиваться под контейнер, в который его положили, а не
предполагать, что он всегда занимает всю ширину экрана.

## SEO

Вёрстка должна быть пригодна для индексации и ранжирования, не только
визуально соответствовать макету.

- Семантические теги вместо `div`-супа: `header`, `nav`, `main`, `section`,
  `article`, `footer` для соответствующих смысловых блоков макета (шапка,
  секции лендинга, футер и т.п.), интерактивные элементы — `button`/`a`, а не
  `div` с обработчиком клика.
- Один `h1` на страницу (обычно это заголовок hero-секции), дальше заголовки
  секций — `h2`, подзаголовки внутри секции — `h3` и т.д., без пропуска
  уровней и без использования заголовков ради размера шрифта (размер — через
  Tailwind-классы/токены, а не через выбор тега).
- `title` и `meta description` в `index.html` — конкретные и по смыслу
  проекта/страницы, не дефолтные заглушки (`frontend-developer` и т.п.);
  Open Graph (`og:title`, `og:description`, `og:image`) — если лендинг
  предполагается шарить в соцсетях.
- Ссылки — с содержательным текстом (не «читать далее»/«тут»), картинки —
  с `alt` (см. «Адаптивные изображения»), важные для LCP изображения (hero)
  без `loading="lazy"`, остальные — с `loading="lazy"`.
- Не блокировать контент от индексации: текст в макете — реальный текст в
  DOM (не текст, зашитый в картинку/SVG), если только это не декоративный
  элемент.

## Производительность (PageSpeed Insights)

Держать в уме Core Web Vitals (LCP, CLS, INP) при вёрстке, а не оптимизировать
постфактум:

- Изображения — в современных форматах (`webp`/`avif`), экспортированные из
  Figma под реальный размер отображения (не тащить 1920px картинку туда, где
  она рендерится на 400px); у hero-изображения (обычно оно и есть LCP-элемент)
  — `fetchpriority="high"`, без `loading="lazy"`.
- Явные `width`/`height` или `aspect-ratio` у всех изображений и медиа-блоков
  — чтобы браузер резервировал место и не было сдвига layout (CLS) при
  подгрузке (перекликается с «Адаптивные изображения»).
- Шрифты (в макете — General Sans, местами Kobzar KS) — подключать локально
  через `@font-face` с `font-display: swap`, не грузить с внешних CDN синхронно;
  использовать только реально применяемые начертания/веса, а не весь семейство.
- Тяжёлые CSS-эффекты из Figma (`backdrop-blur`, множественные `blur`/тени на
  больших областях, как в блоках Presets/Choose/телефонном мокапе) — применять
  точечно, на небольших элементах, не на полноэкранных секциях: это ощутимо
  нагружает отрисовку и бьёт по INP/скроллу.
- Компоненты, не нужные на первом экране (секции ниже fold, тяжёлые виджеты) —
  через `React.lazy`/`Suspense`, чтобы не раздувать основной JS-бандл.
- Не тянуть лишние зависимости ради одной анимации/иконки — если задачу
  решает CSS или маленький инлайновый SVG, не устанавливать библиотеку.
